Case Study / Replay of the August 2026 Incident

What Would Have Happened in August 2026 on a Hardened GCP VM (WAF + Restricted Access)?

The August 2026 incident succeeded because three weaknesses lined up at the same time on an exposed VM. Here is how locking down the existing GCP VM with Load Balancer + Cloud Armor WAF + Restricted External Access (IAP) stops every stage:

August 2026 Failure Point What Happened on the Unprotected VM (Aug 10 to 13, 2026) What Happens on Hardened GCP VM (Load Balancer + WAF / IAP)
1. Unauthenticated Attack on Password Reset API Reached Metabase Directly
An external automated scanner sent 483 requests to POST /api/session/reset_password without logging in, using a SQL injection bug (CVE-2026-72898) to create admin sessions.
 100% Blocked at Google's Edge
Cloud Armor WAF (sqli-v33-stable) blocks the SQL injection payload at the Load Balancer and throttles /api/session/*. With Google IAP (or external access restriction) active, unauthenticated requests are rejected with 401 Unauthorized before touching the VM.
2. Accidental Open Port 3000 Firewall Bypass Bypassed Web Server
A broad GCP firewall rule (airflow-8080) accidentally opened port 3000 across all VMs. The attacker connected straight to the VM IP on port 3000, bypassing nginx.
 Closed & Restricted to LB Only
Port 3000 is bound strictly to 127.0.0.1 (loopback) and the VM firewall only accepts ingress from Google's Load Balancer ranges (35.191.0.0/16, 130.211.0.0/22). Direct IP probing fails completely.
3. 4-Day Patch Delay (Aug 6 Fix vs. Aug 10 Attack) No Edge Shield During Delay
Metabase published the security fix (v0.63.5) on August 6. Because there was no WAF or IAP in front of the VM, the unpatched server was exposed on August 10.
 Edge Shield + Automated Docker Update
Cloud Armor WAF and restricted external access shield the VM even before a patch is applied, while a scheduled weekly job updates the Docker container automatically.

Chapter 05 / Alternative BI Tools

What Do We Lose If We Switch to Lightdash or Tableau?

Both Lightdash and Tableau are respected tools, but switching away from Metabase means giving up core workflows that Modinity uses thousands of times a day.

Option 5 Deep Dive: Lightdash Cloud Pro (~Rp 583M/yr Flat Fee)

Why Lightdash Looks Attractive on Paper, and What Actually Breaks

Lightdash is built specifically on top of dbt (the data transformation tool Modinity uses) and charges a flat monthly workspace fee (~$2,400 to $3,000/month) for unlimited users instead of charging per viewer. However, checking our live Metabase usage reveals 4 major capabilities we would lose immediately:

1. We Lose Instant Custom SQL Charts
4,446 Charts

61% of Modinity's charts are custom SQL queries built in seconds by analysts or AI. In Lightdash, charts are supposed to be defined in Git code files (schema.yml) first. Raw SQL charts in Lightdash cannot use standard semantic filters and cannot even be duplicated with a button.

2. We Lose Live Odoo ERP Reporting
242,098 Queries

In the last 90 days, Modinity ran 242,098 queries across 85 charts directly against our live Odoo database. A Lightdash project can only connect to one database (BigQuery). We could no longer combine live Odoo data and BigQuery data in one place.

3. Business Users Wait on Engineers
2,809 GUI Charts

In Metabase, as soon as a table exists in BigQuery, business users can click and summarize it (2,809 charts built this way). In Lightdash, a table or column is completely invisible to business users until a data engineer writes YAML code for it and deploys it.

Option 6 Deep Dive: Tableau Cloud Standard (~Rp 1.69B/yr Forecasted)

Why Tableau Is the Most Expensive & Disruptive Option

With 6 Creator seats ($75/mo), 0 Explorer seats, and 408+ Viewer seats ($15/mo), Tableau costs more than any other option while slowing down our data & AI delivery:

1. Requires 1-Year Upfront Contract
Rp 1.42B+ Upfront

Unlike Metabase or Cloud Run (which can be paid monthly), Tableau Cloud requires signing an annual contract paid upfront, locking Modinity in before a single dashboard is migrated.

2. Downgrades 408 Users to Read-Only
0 Explorers

In Metabase, all 414 users can build their own views and pivot tables. In Tableau, $15/mo Viewers are strictly read-only. Allowing brand or finance leads to build their own views requires upgrading them to $42/mo Explorer seats.

3. Breaks AI Dashboard Creation
407 Dashboards

Tableau dashboards are complex desktop files (.twb XML), not simple SQL cards. Even with tableau-mcp, AI cannot read chart SQL or update a single chart on a live dashboard, and our 6 analysts would spend 3 to 6 months rebuilding 407 dashboards by hand.

Chapter 06 / Implementation & Continuity

Zero Capability Loss & 1-Day Rollout Plan

Whether we choose Option 2 (Hardened Existing GCP VM at ~Rp 21.6M/yr) or Option 4 (Metabase Pro Cloud at ~Rp 1.39B/yr), our team loses zero functionality and rollout takes less than 1 day.

Will Creating Dashboards from Antigravity Change or Downgrade?

No. It works 100% identically in both the Hardened GCP VM and Metabase Pro Cloud. Our Antigravity workflow uses Metabase's standard web API (/api/card and /api/dashboard) to write SQL queries, create charts, and arrange 24-column dashboard layouts automatically. On our existing GCP VM, zero config changes are needed; on Metabase Pro Cloud, we simply update the URL and API key.

Rollout Plan A: Harden Existing GCP VM (~1 to 2 Hours, Zero Migration)

How We Lock Down Our Existing GCP VM (DevOps Aligned)

  • Step 1 (Zero App/DB Migration): Keep the existing Metabase VM and Postgres database as-is (all 407 dashboards, 7,365 charts, and 9 database connections stay untouched).
  • Step 2 (30 mins): Place the existing VM into an Unmanaged Instance Group behind a Global HTTPS Load Balancer and restrict the VM firewall to accept traffic only from Google Load Balancer IPs.
  • Step 3 (30 mins): Attach Google Cloud Armor WAF (blocking SQL injection sqli-v33-stable and throttling /api/session/*) and optionally enable Google IAP for external access control.
  • Step 4 (15 mins): Enable a scheduled weekly container update check and BigQuery scan volume alert.
Rollout Plan B: Metabase Pro Cloud (~1 Day via Built-in Tool)

How We Move to Official Metabase Pro Cloud (SaaS Risk Transfer)

  • Step 1 (15 mins): Open Admin -> Settings -> Cloud inside our current Metabase and click Migrate to Metabase Cloud.
  • Step 2 (Automatic): Metabase automatically packages all 407 dashboards, 7,365 charts, user accounts, and folder permissions into a cloud snapshot and provisions our new Pro Cloud instance.
  • Step 3 (1 to 2 hours): Re-enter database passwords (BigQuery service account and Odoo replica) in the new Cloud admin screen.
  • Step 4 (1 hour, handled by AI): Antigravity updates the URL and API key in our local MCP config, ge-mcp (Gemini Enterprise), and Modibot, and updates any audit queries to use Pro's Usage Analytics tables.

Summary Recommendation for Executive Decision

1. If Cost & Practical GCP Defense Is the Priority (~Rp 21.6M/year): Keep our existing GCP VM and let DevOps & InfraSec attach the Global HTTPS Load Balancer + Cloud Armor WAF / Restricted External Access. It requires zero database or container migration, blocks external SQLi sprays at Google's edge, and preserves 100% of our 407 dashboards, audit logs, and AI tools.

2. If 100% Vendor Risk Transfer Is the Priority (~Rp 1.39B/year): Choose Metabase Pro Cloud (never Starter or Tableau). It transfers 24/7 server patching and SOC 2 compliance to Metabase Inc., migrates in 1 day, and preserves our Komdigi UU PDP audit trail (query_execution equivalent) and AI workflows.

DevOps Engineering Review (Farid)

Why Keeping the Existing GCP VM Beats Re-Platforming to Cloud Run

Host Responsibility ("Risk Transfer") vs. Open-Source Maintenance

  • The Real Question Is the Host Custodian: In any self-hosted open-source deployment on GCP, Modinity's internal team carries the operational cost and responsibility of securing the host, monitoring WAF logs, and applying patches.
  • When SaaS Is Justified: If management wants to transfer host & patching responsibility to an external party, we must use a managed SaaS.
  • Why SaaS Must Be Pro Cloud (Not Starter): Even with SaaS, Modinity remains the legal Data Controller under Indonesian law (UU PDP / Komdigi). Because Metabase Starter hides the internal query_execution audit log, InfraSec would be blind during an account breach. Only Metabase Pro Cloud (~Rp 1.39B/yr) provides both SaaS risk transfer and full audit logs.

3. Edge Hardening Runbook on the Existing GCP VM (~1.5 Hours, Zero Downtime)

Attaching Cloud Armor WAF to Our Current VM (No Cloud Run Migration Needed)

# Step 1: Create Cloud Armor WAF Policy (Blocks CVE-2026-72898 SQLi payload & throttles /api/session/*)
gcloud compute security-policies create modisight-waf-policy

gcloud compute security-policies rules create 1000 \
  --security-policy=modisight-waf-policy \
  --expression="evaluatePreconfiguredWaf('sqli-v33-stable') || evaluatePreconfiguredWaf('lfi-v33-stable')" \
  --action=deny-403

gcloud compute security-policies rules create 2000 \
  --security-policy=modisight-waf-policy \
  --expression="request.path.startsWith('/api/session/')" \
  --action=throttle \
  --rate-limit-threshold-count=20 \
  --rate-limit-threshold-interval-sec=60 \
  --conform-action=allow \
  --exceed-action=deny-429 \
  --enforce-on-key=IP

# Step 2: Attach policy to the existing VM's Backend Service on the Global HTTPS Load Balancer
gcloud compute backend-services update modisight-vm-backend \
  --security-policy=modisight-waf-policy \
  --global

# Step 3: Lock down VM firewall so attackers cannot bypass the Load Balancer by hitting the VM IP directly
gcloud compute firewall-rules create allow-lb-to-modisight-vm \
  --network=default \
  --action=ALLOW \
  --rules=tcp:80,tcp:443 \
  --source-ranges=35.191.0.0/16,130.211.0.0/22 \
  --target-tags=modisight-vm
